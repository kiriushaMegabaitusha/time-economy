# Codebase Architecture Audit Report

## Executive Summary

The Time Economy application implements a timebanking system with multiple interfaces (Web, TUI, CLI). The overall architecture is reasonably well-organized with clear separation between models, services, and routers. However, there are significant issues with **duplicated logic**, **inconsistent patterns**, and **mixed responsibilities** that should be addressed.

---

## Critical Issues (Priority 1)

### 1. Duplicated `calculate_balance()` Function

**Locations:**
- `app/services.py:16-32`
- `app/routers/members.py:269-287`

**Problem:** The same function exists in two places. The version in `services.py` is the canonical one, used by CLI and TUI. The version in `routers/members.py` is redundant and could drift out of sync.

**Recommendation:** Remove `calculate_balance()` from `routers/members.py`. Keep only the version in `services.py`.

---

### 2. Business Logic Duplicated in Routers

**Problem:** Every router re-implements CRUD operations that already exist in `services.py`:

| Router | Functions Duplicated | Service Equivalents |
|--------|---------------------|---------------------|
| `routers/members.py` | `create_member`, `update_member`, `delete_member` | `services.create_member`, `services.update_member`, `services.delete_member` |
| `routers/transactions.py` | `create_transaction`, `complete_transaction`, `dispute_transaction`, `reopen_transaction`, `update_transaction`, `delete_transaction` | All in `services.py` |
| `routers/needs.py` | `create_need`, `fulfill_need`, `close_need`, `reopen_need`, `update_need`, `delete_need` | All in `services.py` |
| `routers/governance.py` | `create_governance`, `vote_governance`, `update_governance_status`, `update_governance`, `delete_governance` | All in `services.py` |

**Impact:** Maintenance burden, potential for inconsistency, larger codebase to maintain.

**Recommendation:** Refactor all routers to delegate to service layer functions. Routers should only handle HTTP concerns (request parsing, response formatting).

---

### 3. Dashboard Logic Duplicated in `main.py`

**Problem:** `main.py:27-100` re-implements dashboard data fetching that already exists in `services.get_dashboard_stats()`.

```python
# main.py lines 27-100 - duplicated logic
total_members = db.query(models.Member).filter(...).count()
total_transactions = db.query(models.Transaction).count()
# ... many more queries

# Should use:
# stats = get_dashboard_stats(db)
```

**Same issue exists for:**
- Members page (`main.py:103-111`) - duplicates `get_member_balances()`
- Transactions page (`main.py:142-153`) - duplicates `get_all_transactions()`
- Needs page (`main.py:156-166`) - duplicates `get_all_needs()`
- Governance page (`main.py:169-179`) - duplicates `get_all_governance()`
- Skills page (`main.py:182-196`) - duplicates `get_skills_directory()`

**Recommendation:** Replace inline queries with calls to service layer functions.

## High Priority Issues (Priority 2)

### 4. N+1 Query Problem in `main.py`

**Locations:** Lines 53-54, 147-148, 161, 187-188, etc.

**Problem:**
```python
# Executed in a loop - N queries
for t in transactions:
    t.from_member = db.query(models.Member).filter(Member.id == t.from_member_id).first()
    t.to_member = db.query(models.Member).filter(Member.id == t.to_member_id).first()
```

**Recommendation:** Use SQLAlchemy `joinedload()` or relationship loading to fetch related entities in a single query:
```python
transactions = db.query(Transaction).options(
    joinedload(Transaction.from_member),
    joinedload(Transaction.to_member)
).all()
```

---

### 5. Mixed API and Web Route Handlers

**Problem:** Each router has both JSON API endpoints and HTML form handlers:

```python
@router.post("/", response_model=schemas.Member)  # JSON API
def create_member(member: schemas.MemberCreate, db: Session = Depends(get_db)):

@router.post("/web-create")  # HTML Form
def create_member_web(name: str = Form(...), ...):
```

**Impact:** Routers violate single responsibility, making testing harder and code harder to navigate.

**Recommendation:** Consider splitting into:
- `api/` - JSON REST endpoints
- `web/` - HTML form handlers with template rendering

Alternatively, use FastAPI's APIRouter with separate routers for API vs web.

---

### 6. Duplicate Route Patterns

**Problem:** Every CRUD operation has both JSON and web variants:
- `POST /members` + `POST /members/web-create`
- `PUT /members/{id}` + `POST /members/{id}/update-web`
- `DELETE /members/{id}` + `POST /members/{id}/delete-web`

This doubles the number of endpoints and makes maintenance harder.

**Recommendation:** 
1. Use a single API endpoint that returns JSON
2. Have web templates make AJAX calls to the API
3. Or use a single endpoint that handles both (FastAPI can return HTML or JSON based on request)

## Medium Priority Issues (Priority 3)

### 7. Hardcoded Magic Numbers

**Locations:** Multiple files
- `services.py:83-96` - Balance thresholds (>20, <-10)
- `main.py:65-78` - Same thresholds duplicated
- `templates/dashboard.html:157-162` - Same thresholds in JS

**Problem:** Business rules are scattered across the codebase.

**Recommendation:** Create a config module:
```python
# app/config.py
class EconomyConfig:
    CREDIT_CAP = 20
    DEFICIT_LIMIT = -10
    INITIAL_CREDIT = 5.0
```

---

### 8. Inconsistent Session Management

**Problem:** Different patterns for database sessions:
- Routers: `db: Session = Depends(get_db)` (FastAPI dependency injection)
- CLI/TUI: `db = get_session()` followed by `db.close()` (manual)
- Services: `get_session()` returns a session that needs to be closed manually

**Recommendation:** Standardize on a pattern. Consider a context manager:
```python
@contextmanager
def get_db_session():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

---

### 9. Path Manipulation in Multiple Files

**Locations:**
- `app/cli.py:16`
- `app/simple_cli.py:22`
- `app/tui/app.py:13`

```python
sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
```

**Problem:** This is a workaround for not installing the package properly. Can cause import issues.

**Recommendation:** Install the package with `pip install -e .` and remove all path manipulation.

---

### 10. Inconsistent Naming Conventions

**Problem:** 
- Transactions use: `complete`, `dispute`, `reopen`
- Needs use: `fulfill`, `close`, `reopen`
- No clear pattern

**Recommendation:** Establish consistent verbs for state transitions:
- `complete` / `cancel` / `reopen`
- Or: `fulfill` / `cancel` / `reopen`

---

## Low Priority Issues (Priority 4)

### 11. Verbose CLI Imports

**Location:** `app/cli.py:27-38` - 12 lines of imports

**Recommendation:** Use package re-exports in `app/__init__.py`:
```python
# app/__init__.py
from .services import *
```

---

### 12. Export Functions in `simple_cli.py`

**Location:** `app/simple_cli.py:896-1025`

**Problem:** Export functions are in the CLI module but could be reusable.

**Recommendation:** Move to `app/utils/export.py`:
```python
# app/utils/export.py
def export_csv(db, filename): ...
def export_json(db, filename): ...
def export_text(db, filename): ...
```

---

### 13. Missing Error Handling in Service Layer

**Problem:** Most service functions silently return `None` when operations fail, without logging or distinguishing between "not found" and other errors.

**Recommendation:** Consider raising specific exceptions:
```python
class NotFoundError(Exception): pass
class ValidationError(Exception): pass
```

12. **Add proper error handling**

## Summary

The codebase has a solid foundation (models, services, templates) but suffers from:
1. **Significant code duplication** between routers and services
2. **Mixed responsibilities** in main.py
3. **N+1 query problems** throughout
4. **Inconsistent patterns** for common operations

Addressing these issues will improve maintainability, reduce bugs, and make future development easier.
